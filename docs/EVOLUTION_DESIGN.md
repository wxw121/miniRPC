# MiniRPC 连续演进设计

## 1. 目的与范围

本项目维持一个持续演进的当前版本，不再按发布版本拆分功能。本设计用于约束后续功能的实现顺序、接口边界和验收标准，避免在轻量 RPC 框架中堆叠彼此冲突的能力。

当前基础能力包括：Netty 通信、自定义协议、Hessian/Protostuff 序列化、ZooKeeper 注册发现、负载均衡、熔断限流、同步/异步调用、Spring Boot Starter 和优雅停机。

本轮演进目标：在不引入消息队列、分布式事务或服务网格依赖的前提下，使框架具备可诊断、可控重试、可安全部署和可验证的基础工程能力。

非目标：跨语言 SDK、持久化的失败补偿、全局事务、多注册中心复制。这些能力需要独立的存储模型和运维边界，不应混入当前调用链。

## 2. 总体架构与边界

```text
业务代码
  -> 动态代理 / RpcContext
  -> 客户端拦截器（追踪、指标、deadline、重试准入、限流、熔断）
  -> 服务发现 + 本地端点健康状态 + 负载均衡
  -> Netty 传输（可选 TLS）
  -> 服务端拦截器（认证、deadline、指标、过载保护）
  -> 业务线程池 + 本地服务注册表
```

各层只承担一种职责：

- `rpc-common`：协议字段、稳定错误码、调用上下文和 SPI 契约；不依赖 Spring、Netty 或 ZooKeeper。
- `rpc-core`：请求生命周期、传输、端点健康、过载控制和拦截器执行。
- `rpc-registry`：实例的发布、发现与订阅；只维护静态实例元数据，不能写入客户端本地健康判断。
- `rpc-spring-boot-starter`：配置绑定、自动装配、Micrometer/健康端点等框架集成。

## 3. 核心设计决策

### 3.1 请求上下文和协议元数据

新增不可变 `RpcContext`，由代理在一次调用开始时创建，并在客户端、服务端拦截器之间传递。上下文包含：

- `requestId`、`traceId`；
- 绝对截止时间 `deadlineEpochMillis`；
- `idempotencyKey`（仅业务显式传入时携带）；
- 受限的 `attachments`（白名单键、单项与总大小上限）。

协议只传递必要字段；未知字段必须忽略，以允许后续兼容扩展。服务键统一为 `(interfaceName, version, group)`，禁止只按接口名发现服务。

### 3.2 超时、取消与重试

`deadline` 是调用生命周期的唯一时间预算：服务发现、连接、排队、网络等待和重试都必须消耗该预算。任何阶段剩余时间不够时立即返回 `DEADLINE_EXCEEDED`，不得再启动重试。

重试只允许同时满足以下条件的请求：方法标记 `@RpcIdempotent`、失败类型在白名单内、仍有 deadline 预算、尚未超过重试预算。写操作默认 fail-fast；需要去重的写操作由业务提供幂等键，框架不猜测其幂等性。

错误码使用稳定枚举，例如 `UNAVAILABLE`、`DEADLINE_EXCEEDED`、`OVERLOADED`、`UNAUTHORIZED`、`SERIALIZATION_ERROR`、`INTERNAL`。异常仅是本地表现形式，跨网络的控制逻辑必须依据错误码。

### 3.3 端点健康与流量保护

客户端维护独立的 `EndpointHealth`：按端点记录连续失败、短暂摘除截止时间和恢复探测状态。负载均衡只从“注册中心存在且本地未摘除”的实例中选择；成功调用逐步恢复权重，持续失败则临时摘除。此状态不能回写 ZooKeeper，避免单个消费者影响全局路由。

服务端继续采用有界业务线程池。队列满时立即返回 `OVERLOADED`，并记录拒绝指标；禁止在 Netty IO 线程执行降级后的业务代码。熔断半开探测必须受 permit 上限约束。

### 3.4 可观测性

核心层暴露无依赖的事件/拦截器钩子；Starter 将其适配为 Micrometer 指标和 OpenTelemetry Trace。最小指标集：调用数、成功/失败数、耗时直方图、超时数、重试数、熔断拒绝数、线程池拒绝数、连接池活跃数。

日志以 `requestId`、`traceId`、服务键和目标端点关联。业务参数及响应体默认不记录，避免泄露敏感信息与制造高基数指标。

### 3.5 安全边界

网络协议继续拒绝 JDK 原生反序列化。后续新增 TLS 开关和 `SslContext` 配置；服务端支持可选 mTLS，认证由服务端拦截器完成。认证凭据只放入受限附件，不能输出到日志或指标标签。

默认仍允许本地开发的明文直连；一旦配置了远程暴露地址，应在启动时明确告警。TLS/mTLS 的证书来源、轮换和信任策略由部署环境提供，不在框架中内置证书管理。

## 4. 实现顺序

### 步骤 1：契约、配置与文档基线

1. 更新 README、架构文档、协议文档和变更日志，反映网络序列化限制、`version/group`、幂等重试规则和实际配置项。
2. 为配置增加启动期校验：端口、线程池、队列、超时、连接池、序列化类型、ZooKeeper base path。
3. 固化稳定错误码，并补齐请求/响应对错误码的编码与解码。
4. 明确兼容性：旧的网络 JDK 序列化配置启动即失败；若需要保留旧 `@RpcReference` 属性，应仅作为废弃别名，不能覆盖统一客户端配置。

完成标准：配置错误不在首次调用时才暴露；文档示例可直接运行；所有兼容性断点都有迁移说明。

### 步骤 2：调用生命周期闭环

1. 引入 `RpcContext` 与 deadline 传播。
2. 将连接、发送、等待响应和 Future 清理统一到同一 deadline。
3. 以错误码替代跨端依赖异常文本的判断。
4. 为异步调用增加取消传播：调用方取消后移除本地 Future；服务端仅在尚未执行业务前允许取消。

完成标准：超时、取消、断连不会遗留 Future、请求计数或线程池任务；同步与异步的错误语义一致。

### 步骤 3：可观测性与服务端可运维性

1. 在客户端和服务端调用链统一埋点。
2. Starter 提供 Micrometer 和 OpenTelemetry 可选集成。
3. 提供 readiness/liveness 健康信息：注册状态、线程池饱和、连接状态、优雅停机状态。
4. 将指标、日志和 trace 的字段命名写入文档，避免后续任意变更。

完成标准：一次失败调用可通过 traceId 定位到目标端点、错误码、重试次数和服务端拒绝原因。

### 步骤 4：端点健康与重试治理

1. 实现客户端本地端点摘除与恢复探测。
2. 将 `@RpcIdempotent`、错误码白名单、最大尝试次数和 deadline 预算组合为统一重试策略。
3. 加入抖动退避与重试预算，防止实例故障时放大流量。
4. 让负载均衡跳过临时摘除端点，并保留服务预热权重。

完成标准：单个实例故障不会造成无效重试风暴；写请求不会因默认重试而重复执行。

### 步骤 5：安全传输与认证

1. 为 Netty 客户端和服务端加入 TLS 配置与证书加载。
2. 增加 mTLS 可选模式及认证拦截器 SPI。
3. 对协议附件、帧长、认证失败和反序列化失败执行统一限额与错误码处理。
4. 提供本地明文、TLS、mTLS 三种可运行样例。

完成标准：启用 TLS 后所有 RPC 与心跳均走加密通道；认证失败不会进入业务线程池。

## 5. 失败处理矩阵

| 场景 | 客户端行为 | 服务端行为 |
|---|---|---|
| 找不到服务 | 返回 `UNAVAILABLE`，不重试 | 不适用 |
| 连接/节点断开 | 标记端点失败；仅幂等请求在预算内重试 | 释放连接相关资源 |
| deadline 耗尽 | 立即完成 Future 并清理 | 未执行业务则拒绝；执行中只记录超时 |
| 业务线程池满 | 返回 `OVERLOADED`，不盲目重试 | 不在 IO 线程执行任务 |
| 认证失败 | 返回 `UNAUTHORIZED`，不重试 | 不进入业务调用 |
| 序列化或协议非法 | 返回 `SERIALIZATION_ERROR` 或关闭连接 | 记录安全审计事件，拒绝请求 |

## 6. 测试与验收

- 单元测试：deadline 计算、重试准入、错误码映射、端点摘除恢复、附件限额、配置校验。
- 集成测试：真实 ZooKeeper、Provider/Consumer 进程、服务注册变更、优雅上下线、TLS/mTLS 握手。
- 故障注入：断网、半开连接、慢响应、重复响应、线程池耗尽、注册中心短暂不可用。
- 兼容性测试：新旧服务键、协议未知字段、禁用 JDK 网络序列化的失败提示。
- 性能测试：独立 JMH 或独立 Maven profile 运行；不得占用默认单元测试端口或影响 `mvn test`。

每项新增能力必须同时提交：实现、回归测试、配置说明、示例或迁移说明。没有可观测性与故障测试的可靠性功能不视为完成。

## 7. 后续文档维护规则

每次修改协议、配置、公共注解或默认行为时，必须在同一变更中更新：`README.md`、`docs/ARCHITECTURE.md`、`docs/PROTOCOL.md`、`docs/FEATURES.md` 和 `CHANGELOG.md` 中受影响的内容。示例代码必须由自动化测试或构建校验覆盖。
